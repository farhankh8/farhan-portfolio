Case studies

Three problems that were worth solving

Each of these started as a specific defect with a specific cost, and each ended with a measurement rather than a promise.

Float drift in a financial ledger

Problem

Revenue reconciliation was off by between 0.01 and 0.50 currency units per transaction, because IEEE 754 floating point cannot represent every decimal exactly.

Solution

A Python data engine on DuckDB and PyArrow using the Decimal128 exact decimal currency type, so every amount stays a decimal from ingestion to report.

Result

Zero float drift, 2,061 tests passing, 0.4 second cold boot, and output a finance team can audit.

Technical notes

Numeric data types, decimal precision, data validation, transformation consistency, analytical reconciliation.

AI Business Intelligence Platform

Ten airlines, no source of truth

Problem

Airline performance pulls together several interconnected measures, including capacity, passenger traffic, revenue and operational indicators, and there was no single source of truth across the ten modelled carriers. Source data changed silently between refreshes without anyone noticing.

Solution

SHA-256 canonical hash verification across 34 data manifests, with a star schema dimensional model underneath the reporting layer.

Result

34 of 34 manifests verified, 120 executive visuals and 609 of 609 tests passing.

Technical notes

Dimensional modelling, Power Query transformations, DAX calculations, revenue and passenger metrics, dashboard organisation.

AEROVISION 360

Invoicing by hand

Problem

GST invoicing was manual, so tax calculations drifted and delivering a PDF to a client took a separate round of work every time.

Solution

An automated GST engine with Zod validation on the input, Razorpay webhooks for payment state, and jsPDF for instant export.

Result

322 production deployments with zero downtime releases, four tier role based access, and the app running live.

Technical notes

Frontend application structure, backend APIs, database integration, user access management, invoice workflows, project and task management.

How I work

Four habits I bring with me

Product thinking

Reading a requirement properly before writing any of it, so the feature that ships is the one that was actually asked for. Most of my projects started from a person doing the same task badly by hand.

Data first

Deciding what the number means before deciding how to display it. If the source is ambiguous, the chart is decoration and I would rather fix the source.

Business context

Understanding the process behind the software: what closes a month, what a finance lead signs, what a tax split has to contain. The ERP and accounting work is what makes the engineering decisions defensible.

Continuous development
